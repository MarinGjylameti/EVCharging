DRIVER

ADMIN

SUPERADMIN

# 11. CHARGER INTEGRATION

The requirements describe receiving data from charging equipment, but they do not define the exact hardware vendor/protocol.

Therefore do NOT hardcode the domain to one charger manufacturer.

Create a clean charger integration boundary such as an adapter/gateway interface.

Domain/application code should consume normalized events rather than vendor-specific payloads.

Examples conceptually include:

VehicleConnected
ChargingStarted
MeasurementReceived
ChargingStopped
VehicleDisconnected
ChargerFaulted
StatusChanged

These names are examples, not mandatory API names.

If no real charger API/protocol has been provided yet, do NOT fabricate a production integration.

Instead:

- establish the integration contract;
- create test fixtures / simulator support necessary for development and automated testing;
- clearly isolate it from production integrations.

When the real charger protocol/API is supplied later, implementing an adapter should not require rewriting Charging Sessions, Pricing, Admin or UI logic.

Take into account:

- duplicate events;
- retries;
- events arriving out of order where realistically possible;
- reconnects;
- stale data;
- temporary network failures;
- missing optional telemetry.

Do not assume that external devices always behave perfectly.

# 12. CHARGING SESSION CONSISTENCY

Charging sessions are financially relevant even though electronic payments are not currently implemented.

Be careful with data correctness.

A charging session should preserve enough historical information to reproduce its calculated cost.

For example, if the administrator changes a charging point from €0.35/kWh to €0.40/kWh tomorrow, a historical session performed at €0.35/kWh must NOT change its cost.

Use the appropriate price snapshot/history strategy.

Money values must never rely on floating-point arithmetic.

Use decimal / numeric values with appropriate precision.

Charging energy, duration and price calculation rules should exist in testable domain/application logic rather than being implemented separately by each client.

The backend should produce the authoritative calculated cost.

# 13. CHARGING POINT STATUS MODEL

Do not treat statuses as arbitrary strings.

- new state;
- timestamp;
- reason.

Think carefully about interactions between:

- device-reported state;

The final state model should have deterministic behavior and be documented.
